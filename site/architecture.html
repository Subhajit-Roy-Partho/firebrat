Under the hood

From PDF to a synced, offline audiobook

Firebrat has two independent halves that only touch through a portable book-package format: a conversion pipeline that runs once per book, and a Flutter reader that never needs the pipeline again afterward. A second, optional pipeline for multi-voice novels ends in the same package format.

1

Extract

Layout-aware parsing (marker-pdf + PyMuPDF) pulls per-page text, headings, figure crops, and full-page renders out of the source PDF, assigning every figure/table a stable id.

2

Compile

An LLM groups raw pages into logical sections, rewrites dense text into clean narration, and — critically — recognizes mathematical relationships in the prose and authors real LaTeX for them.

3

Narrate

A local text-to-speech model synthesizes one audio clip per sentence, then Firebrat concatenates them and tracks each clip's real, sample-derived duration to build exact start/end timestamps.

4

Package

Manifest, audio, and assets are bundled into one self-contained .tar.gz — servable over HTTP, or copied straight onto a device.

Why formulas needed a different approach

The naive assumption going in was that a PDF's formulas could be extracted as LaTeX the same way its figures are extracted as images. That assumption held for exactly zero real formulas in testing. Real technical books very often typeset math as plain inline text — tCK = 1/f = 10 ns — not as a distinct, taggable equation block. There's nothing for a PDF parser to extract, because there's no structured math in the source file to begin with.

So formulas in Firebrat are LLM-authored, not extracted. The same model that writes narration text is asked to recognize a mathematical relationship in the surrounding prose and write real LaTeX for it directly. Firebrat's own code — never the model — then mints the formula's id and adds it to the book's asset catalog. This keeps the same invariant that governs figures and tables (an id always comes from code, never from a model's output, which removes an entire class of hallucination bugs) while acknowledging that the LaTeX itself has to come from somewhere the extraction stage simply doesn't have access to.

Why per-sentence synthesis instead of forced alignment

An alternative design would synthesize a whole section's narration as one long audio clip, then run a separate forced-alignment model afterward to figure out which words correspond to which timestamps. Firebrat does the opposite: each sentence is its own short TTS call, and the timestamps fall out for free from literally measuring how long each resulting clip is and adding a fixed silence gap between them. No alignment model, no alignment failure modes, no approximate boundaries — the highlight sync is exact by construction, not by inference.

Why offline-first

A mobile audiobook reader should work on a train with no signal. The backend's entire job is producing a complete, self-contained package and handing it over — once — after which the app never needs to talk to it again. That's also what makes a book a genuinely portable file: the same .tar.gz the backend serves over HTTP can just as easily be copied to a phone over USB, shared through a messaging app, or dropped in cloud storage, and the app's built-in file picker will open it identically either way.

The multi-voice pipeline (firebrat_cast)

A second pipeline, for novels, lives beside the technical-book one. It turns an ebook into an audiobook with a distinct voice per character, and ends in the same package format, so no client needs to change.

1

Fetch

Gutenberg EPUB or an uploaded ebook (or a text PDF) becomes clean text, one raw page per unit, boilerplate removed for Gutenberg books.

2

Segment

A deterministic split into quoted speech and narration, each with a stable page and index key.

3

Cast

The LLM builds the character roster, attributes every quote to a speaker and tags emotion. Resumable per chunk; output is cast.json.

4

Synth

Qwen3-TTS makes an anchor voice per character and speaks each line. Text is normalised, silence trimmed and loudness matched.

5

Package

A standard Firebrat package, zipped with audio stored, ready for a client or the Internet Archive.

The cast stage reads the book in two passes: a roster pass over windows of about 3,500 words, then an attribution pass over chunks of at most 600 words and 30 quotes. Each chunk result is cached on disk, several chunks are sent to the model at once, and a regular-expression fallback keeps one bad reply from stopping a book. Stages run as separate processes, each in its own Python environment, so the GPU memory is fully released between them.

Scheduling

One model on the GPU at a time

A 16 GB graphics card cannot hold the casting model and the speech model together, so the scheduler works in phases and batches books to avoid reloading models.

Inbox

Each book is a small JSON file dropped in the scheduler’s inbox/ folder, either by a command-line submit or by the server when someone uploads with Expressive voices.

CPU prefetch any time

Downloads and text extraction need no GPU, so they run as soon as a book arrives.

LLM phase GPU

The scheduler starts a managed vLLM server, casts all waiting books together (up to a configurable cap), then stops vLLM and checks the GPU memory is really free before going on.

Audio phase GPU

Qwen3-TTS narrates the cast books one at a time, shortest first by default, and zips each. Books that arrive during audio wait for the next round. The LLM phase takes priority over audio.

Why vLLM for casting

Casting sends many small requests, so throughput matters. On an RTX 4080 (16 GB), vLLM serving Qwen3.5-9B with FP8 weights (8,192-token context, eight parallel sequences) measured about 152 tokens per second in aggregate, against about 2.3 tokens per second for the same model loaded in-process with 8-bit quantization. In practice casting ran at roughly 8,000 to 23,000 words per minute: a 26.7k-word book in 3 minutes 17 seconds, and an 84k-word book in 3 minutes 37 seconds.

GPU staging lessons

  • Qwen3.5-9B in bf16 (about 18 GB) does not fit in 16 GB.
  • On-the-fly FP8 through the transformers library corrupted the model’s vision tower, so in-process runs use bitsandbytes 8-bit and skip the vision and output-head modules. vLLM’s own FP8 path is what the casting server uses.
  • A stage waits in line for the GPU instead of failing, and the scheduler never kills another process that holds GPU memory.
  • Everything is resumable: state is kept per book on disk, so you can stop and restart the scheduler at any time.

Status. The pipeline code is covered by offline tests, and the casting stage has run on real novels on the GPU server. The speech stage has not yet been verified end to end on real books, and the scheduler itself has not yet been run as the long-lived service. Expect to tune voices after the first listen.

Server administration (opt-in)

If you run your own Firebrat server you can turn on accounts, roles and remote control of the conversion queue. Everything here is off unless you enable it, so existing setups keep working unchanged.

  • Roles. Admin can do everything. User can upload (including Expressive voices) and manage their own books and jobs. Viewer can only listen. Not signed in means public read-only, as before.
  • First admin. The server makes a one-time setup code, stores only a hash of it, and prints it once to the server log (and to a private file that is deleted after use). The first signed-in account to enter it becomes admin. Five wrong tries lock out further attempts for ten minutes. You can instead name admin emails in an environment variable.
  • Invites. An admin pre-approves an email address and a role; the invite is claimed when that verified email first signs in. The last active admin cannot be demoted, disabled or removed. Admin actions are written to an audit log.
  • Model settings. Pick the casting model (Qwen3.5-9B or 4B) and the speech engine from a server-defined list, with VRAM hints and a warning when weights are not downloaded yet.
  • Run pattern. Batched (all queued books cast together, then audio) or sequential (one book end to end); a cap of books per LLM phase; audio order (shortest first or first in first out); quiet hours during which no new GPU phase starts; pause and resume. The scheduler re-reads these settings before every phase, so no restart is needed.
  • Queue control. From the web app and the Android app an admin can see each book’s stage, pause or resume, cancel, or move a book to the top. These act between books and stages; they do not interrupt a stage that is already running.
